## 完整复盘：03 / 04 / 07 同一轮内复发

触发原因：这三个模式都是在本 run 已经点名、开始修之后，同一轮里又出现了新案例（见 bugbook README 的触发标准）。

**时间线**
- 2026-11-19：全面 review 点名 P1-10（测试碰真实环境）、P1-11（失败路径没有测试）、P1-8（配置校验有缺口）。同一天，架构师的探针往真实 usage.jsonl 写了一行（03-2）。
- 2026-11-19：T01 的实现者打开 PROJ_LIVE_TESTS=1（03-3）。
- 2026-11-20：T19 的子代理改了 HOME，误报本机没有 pytest（03-5）；T21 照着评审的修法改，引入回归（04-4）。
- 2026-11-21：终审找出 F6（13 处守卫没有喂坏测试，04-3）和 F8（read_events，07-2）；终审修复期间，调试脚本没有设置 PROJ_CONFIG（03-4）。
- 2026-11-21：/retro 横扫，又找出 01-4。

**多因分析**
1. **修复的范围按点名的条目切**：每个任务只修自己那一条 P1，任务规格里没有「同族横扫」这一步。终审是第一个看全局的环节，所以同族问题都堆到了终审。
2. **隔离只放在了它被发现的地方**：P1-10 是在 pytest 里发现的，所以只修了 conftest。探针和调试脚本在 pytest 之外跑，原来就没有入口可以走，派发词里的「把 HOME、PROJ_CACHE、PROJ_CONFIG 设为 tmp」要每个角色每次手写，漏一个变量就会碰到真实环境。
3. **手写隔离本身有副作用**：改 HOME 会让 pytest 消失，于是角色倾向于少改几个变量，与第 2 条互相加强。

**检测过程**
- 03 的复发都是角色自己报告的，或者领队读报告时发现的，没有任何自动信号。
- 04 和 07 的复发由终审评审发现。

**Lessons**
- 做得好：
  - 变异元测试让「守卫有没有鉴别力」第一次可以机器验证；
  - 重启服务前先对真实配置做只读校验，避免了服务起不来。
- 做得坏：
  - 隔离靠派发词约定，而不是靠入口；
  - 修复任务的规格里没有同族横扫。
- 侥幸：
  - 03 的 4 次复发都只是读取或追加 1 行，没有写坏真实数据，也没有 ssh 到真实主机执行写操作。
