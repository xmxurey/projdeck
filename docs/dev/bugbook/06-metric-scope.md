# 模式 06：同一指标两种口径

## 模式卡
- **所属通用类型**：T05 metric-scope-mismatch
- **一句话定义**：同一个概念，比如「子代理在干活」，在不同位置用不同的数据源、不同的时间窗计算，结果互相矛盾。
- **本仓计数**：1（截至 2026-11-21）
- **为什么在这个仓库反复发生**：会话记录只有事件，没有状态，只能从事件推断。不同出口会选不同的推断方式：通知到达的时刻、文件 mtime、meta 加 600 秒。
- **写代码时如何预防**：每个推断出的状态只定义一处，各出口都调用它；不得不分叉时，把差异写进设计并说明接受的理由。
- **评审时怎么查**：每个时间段或状态的计算，写出起点和终点各自的来源，与同屏其他数字对照。
- **现有守卫**：guards.md G08。
- **相关铁律**：CLAUDE.md 第 1 条。
- **相邻模式**：01。

## 案例

### 案例 06-1：离开 3 小时后才收到通知，这 3 小时整段算成子代理时间
- **commit**：`d98c61f`
- **日期**：2026-11-19 发现
- **症状**：后台任务完成通知到达前的整段等待，被时间线画成了「子代理在干活」。
- **根因**：子代理时间段的终点取的是通知到达时刻，而不是子代理最后一次写入（文件 mtime）。
- **量化影响**：时间线与统计按小时级别失真。
- **为什么测试没拦住**：只测了计算，没测生产链路。设计阶段的挑战者指出，`act_live` 如果不传 spans，原来的测试照样全过。
- **钉住它的测试**：`tests/test_subagent_spans.py`、`tests/test_subagent_spans_spec.py`（端到端经过 `act_live`）
- **同根因第几次**：第 1 次
- **状态**：已修。实时尾段用 `count_subagents`（meta 加 600 秒），历史段用 spans（mtime），两者仍然分叉，设计里写明并接受。
