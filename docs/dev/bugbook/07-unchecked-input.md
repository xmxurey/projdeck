# 模式 07：外部输入不校验类型

## 模式卡
- **所属通用类型**：T06 zero-empty-boundary（主）、T11 undiagnosable-error
- **一句话定义**：配置、缓存、usage 日志这类外部 JSON，代码默认它的类型是对的。类型不对时，可能静默走错，例如字符串被当成列表逐字符迭代；也可能抛出 traceback。
- **本仓计数**：2（截至 2026-11-21），第 2 次是本模式被点名、修复设计已经写好之后发现的，触发了完整复盘。
- **为什么在这个仓库反复发生**：Python 的鸭子类型让错误类型的值也能跑一段，比如字符串可以迭代、`int + str` 到很远才报错；而读取这些文件的代码分散在 config、cli、sync 各处。
- **写代码时如何预防**：
  - 读外部 JSON 的每一处，都按类型校验每个键；
  - 报错点名「第几个 host 的哪个键」，不用 `%r` 输出整个值（值里可能有真实别名，见 R-001）；
  - 逐行读取的日志，坏行要跳过并计数，不能整份丢弃，也不能让整个读取崩溃。
- **评审时怎么查**：
  - grep 新增的 `json.load`、`json.loads`，追到每个取值点，问一句：这个键是错误类型时会怎样；
  - 修复其中一处时，横扫所有读取外部 JSON 的地方。
- **现有守卫**：guards.md G05。
- **相关铁律**：无。
- **相邻模式**：01。

## 案例

### 案例 07-1：`roots` 写成字符串时，从根目录 `/` 开始扫描
- **commit**：`d98c61f`
- **日期**：2026-11-19 发现
- **症状**：
  - `roots` 写成字符串时，会从根目录 `/` 开始扫描；
  - `hosts` 格式写错时，直接打印 traceback；
  - `proj sync <拼错的主机名>` 什么都不做，返回 0。
- **根因**：config 只检查键是否存在，不检查类型；sync 不核对主机名是否存在。
- **量化影响**：扫描 `/` 会让采集超时，主机上的项目全部过期。
- **为什么测试没拦住**：fixture 不含真实形态，只有合法配置。
- **钉住它的测试**：`tests/test_config_validation.py`、`tests/test_config_validation_spec.py`
- **同根因第几次**：第 1 次
- **状态**：已修。合并后重启前，用新代码只读校验了一遍真实配置，通过。

### 案例 07-2：usage.jsonl 里的 ts 不是数字时，`proj report` 崩溃
- **commit**：`d98c61f`（终审修复 F8）
- **日期**：2026-11-21
- **症状**：usage.jsonl 里有一行的 `ts` 不是数字，`proj report` 抛 TypeError 退出。
- **根因**：07-1 只修了 config，`read_events` 是另一处读外部 JSON 的地方，没有被同族横扫到。

- **为什么测试没拦住**：修复时没有做同族横扫。
- **钉住它的测试**：`tests/test_outlets.py::test_read_events_skips_lines_whose_ts_is_not_a_number`
- **同根因第几次**：第 2 次（复发）
- **状态**：已修
