# 模式 08：同一事实写了多份副本

## 模式卡
- **所属通用类型**：T05 metric-scope-mismatch（主，同一个值在两处定义）、T03 label-content-mismatch
- **一句话定义**：同一个值（颜色、白名单、规则、判定）在两处以上分别写死。改了其中一处，其余的悄悄漂移，两个出口对同一件事说两种话。
- **本仓计数**：3（截至 2026-11-24）。
- **为什么在这个仓库反复发生**：
  - 同一个状态有三个出口：网页（app.css、web.py）、终端（ui.py）、Claude Code 状态栏（contrib/ 下的脚本，由 jq 拼 ANSI）。三种语言、三个目录，没有共享常量的通道；
  - 计划按「点名的文件」列触及文件，没有对旧值做全仓 grep，写死旧值的测试和脚本就落在了清单外（run 2026-11-23-d6-d7-display 里，T02、T03、T08 的实现者都要越出触及文件去改写死旧值的测试）；
  - 测试为了「独立」把期望值写成字面量，这是对的（铁律 1）；但同一份白名单在两个测试文件里各抄一遍，就成了两个副本。
- **写代码时如何预防**：
  - 改一个值之前，先 `grep -rn` 它的旧写法（十六进制、`r, g, b`、`r;g;b` 三种），范围包括 projdeck/、contrib/、tests/、docs/，把命中全部列进计划的触及文件；
  - 非 Python 的出口（shell、jq）无法 import 常量时，配一条测试把它钉到 Python 的那个常量上，参见 `tests/test_statusline.py::test_waiting_colour_is_the_terminal_boards_wait_colour`；
  - 退役的值进 G17 的清单（`tests/test_retired_palette.py`），防止它在发布的文件里回来。
- **评审时怎么查**：
  - diff 改了某个字面量时，在 HEAD 上 grep 它的旧值。除了「旧值集合」这类有意保留的副本，任何命中都算发现；
  - 同一个守卫在两个测试文件里各有一份白名单或阈值时，查两份是否一致；不一致就算发现。
- **现有守卫**：guards.md G15（配色取值）、G17（退役颜色不得回到发布文件）。没有通用的「同值多处」检查，只能靠上面的 grep 检法。
- **相关铁律**：CLAUDE.md 第 1 条（同一概念只准一套实现）。
- **相邻模式**：06（同一指标两种口径），01（案例 01-5 的摘要文字与终端显示）。

## 案例

### 案例 08-1：状态栏脚本还用旧的「等你」橙色
- **commit**：`4f1c0e4`（run 2026-11-23-d6-d7-display；T03 评审 ⚠️-1 发现，用户在门禁 B 选「再改」，F-9 修复）
- **日期**：2026-11-23
- **症状**：
  - 终端看板的「等你」改成 `217;89;38` 后，`contrib/statusline-waiting.sh:17` 仍写死 `38;2;240;163;94`；
  - 另有 3 个测试也断言这个旧值。合并的话，同一个状态会出现两种橙色。
- **根因**：颜色在 ui.py 和状态栏脚本里各写了一份，计划只列了 ui.py。
- **量化影响**：合并前修掉，没有进入交付。
- **为什么测试没拦住**：状态栏测试把旧值当期望值，它们钉住的正是那个副本。
- **钉住它的测试**：
  - `tests/test_statusline.py::test_waiting_colour_is_the_terminal_boards_wait_colour`（用 `ui.WAIT_RGB` 拼出色值，断言脚本里就是它）；
  - `tests/test_retired_palette.py`（G17，2026-11-24 /retro 新增；用起点提交 aeb5dbb 版的脚本喂它，用例失败）。
- **同根因第几次**：第 1 次。
- **状态**：已修。

### 案例 08-2：app.css 里同一份任务格填充写了两份
- **commit**：`4f1c0e4`（T01 评审 r2 的 I-1 发现，任务内修复）
- **日期**：2026-11-23
- **症状**：
  - 旧的 `.task-todo/.task-doing/.task-stuck { fill }` 和新的 `.task-cell.task-*` 同时存在，`.task-stuck` 两处都改过一次；
  - 旧规则还会替缺失的 `.task-cell.*` 规则兜底，独立测试对 4 档里的 3 档没有鉴别力。
  - 同一轮里，app.css 还重复定义了 base.css 已有的 `--bg`。
- **根因**：新增规则时没有删掉被它取代的旧规则，理由「li 也用这些类」不成立（`fill` 对 `<li>` 不起作用）。
- **量化影响**：外观没有出错；守卫的鉴别力有缺口。合并前修掉。
- **为什么测试没拦住**：spec 用例按「有效填充」求值，旧规则恰好给出相同的值。
- **钉住它的测试**：`tests/test_web_css.py::test_no_bare_task_fill_rules`。
- **同根因第几次**：第 2 次。
- **状态**：已修。
