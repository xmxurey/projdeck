# 模式 04：守卫测不出它要防的错

## 模式卡
- **所属通用类型**：T02 guard-never-fires
- **一句话定义**：测试或守卫存在，但把实现改错后它照样通过。常见原因有：断言恒真；只断言否定条件；鉴别力依赖机器、负载或内核缓冲区；变异测试定位不到被加强的那条用例。
- **本仓计数**：5（截至 2026-11-21），其中 2 次发生在本模式被点名之后，触发了完整复盘。
- **为什么在这个仓库反复发生**：
  - 很多模块有两份测试，一份是实现者写的 `test_X.py`，一份是独立测试者写的 `test_X_spec.py`，两份都「通过」就容易被当成双重保险；
  - 失败路径要构造 ssh 超时、只读目录、坏字节，成本高，于是只测正向路径。
- **写代码时如何预防**：
  - 每个守卫配一对用例：喂坏数据它会响，喂好数据它保持安静；
  - 写完先在拷贝上做一次忠实变异，注入的错误要与真实错误同源；
  - 变异元测试用 `tests/_mutation.py`，按 node id 定位到具体用例。
- **评审时怎么查**：
  - 对每条新断言问一句：把实现改成最可能的那种错，它会红吗？
  - grep `>= 1`、`in out` 这类宽松断言，以及只有 `not in` 的用例；
  - 涉及超时或缓冲区的断言，检查它的鉴别力是不是取决于数据量或机器。
- **现有守卫**：guards.md G09（变异元测试）。
- **相关铁律**：CLAUDE.md 第 2 条。
- **相邻模式**：03。

## 案例

### 案例 04-1：关键失败路径改错了，测试照样全过
- **commit**：`d98c61f`
- **日期**：2026-11-19 发现
- **症状**：评审把三处实现故意改错，测试照样全过：
  - ssh 运行 agent 时的超时处理；
  - clean/restore 的失败路径；
  - 待办遇到非 UTF-8 时的处理。
- **根因**：这些失败路径零测试。
- **量化影响**：不可量化。
- **为什么测试没拦住**：新代码零测试。
- **钉住它的测试**：`tests/test_failure_coverage_spec.py`（变异元测试）
- **同根因第几次**：第 1 次
- **状态**：已修

### 案例 04-2：20 处断言恒为真或鉴别力不足
- **commit**：`d98c61f`
- **日期**：2026-11-19 发现
- **症状**：review 列出「最可疑的 20 处断言」，例如 `>= 1`、只断言否定条件、把整份输出当成断言对象。
- **根因**：测试复读实现，或者只测「不崩溃」。
- **量化影响**：不可量化。
- **为什么测试没拦住**：测试复读实现。
- **钉住它的测试**：`tests/test_weak_assertions_spec.py`、`tests/test_assertions_t22_spec.py`、`tests/test_assertions_t25_spec.py`
- **同根因第几次**：第 2 次
- **状态**：已修

### 案例 04-3：终审发现 13 处守卫没有「喂坏它响」的用例
- **commit**：`d98c61f`（终审修复 F6）
- **日期**：2026-11-21
- **症状**：这一轮的主题就是补守卫测试，但终审仍然找到 13 处新守卫没有喂坏用例，例如：
  - `from_field` 的解码一侧；
  - `write_atomic` 先 fchmod 收紧到 0600；
  - clean 的 skipped 行做净化。
- **根因**：各任务只为自己点名的那条守卫补了测试，没有对任务里新增的其他守卫做同族盘点。
- **量化影响**：不可量化。
- **为什么测试没拦住**：守卫不在任何「喂坏」测试的链路上。
- **钉住它的测试**：F6 补的用例；13 处守卫逐一去掉后都会被抓住。
- **同根因第几次**：第 3 次（复发）
- **状态**：已修

### 案例 04-4：评审建议的修法引入了回归
- **commit**：`d98c61f`（T21）
- **日期**：2026-11-20
- **症状**：评审建议把 sleep 放在断言之前。照做后，另一条变异不再被抓住，按下葫芦浮起瓢。
- **根因**：修法建议只对着一条变异验证过，没有跑整张变异表。
- **量化影响**：多打回一轮。
- **为什么测试没拦住**：只拿一条变异做验证。
- **钉住它的测试**：最终改为断言、sleep、再断言一次。
- **同根因第几次**：第 4 次
- **状态**：已修

### 案例 04-5：变异元测试靠文本锚点定位，整文件跑、只看返回码
- **commit**：`d98c61f`（终审修复 F2）
- **日期**：2026-11-21
- **症状**：
  - 元测试用文本锚点找变异位置，重构时大面积失配；
  - 子 pytest 跑整个文件、只看 returncode，证明不了被加强的那条用例本身有鉴别力；
  - copytree 把 `.worktrees` 也拷了进去。
- **根因**：每个任务各写一份变异脚手架。
- **量化影响**：不可量化。
- **为什么测试没拦住**：守卫自证。
- **钉住它的测试**：`tests/_mutation.py`（共用 helper，按 node id 定位）
- **同根因第几次**：第 5 次
- **状态**：已修。剩余部分（锚点改成 AST）进 backlog。
