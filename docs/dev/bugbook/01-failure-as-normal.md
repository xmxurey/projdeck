# 模式 01：失败被显示成正常结果

## 模式卡
- **所属通用类型**：T01 silent-failure（主）、T04 stale-as-fresh、T11 undiagnosable-error
- **一句话定义**：读取或采集失败时，代码退回一个「看起来正常」的值（旧状态、`non-git`、「回收站是空的」），用户看不出发生了失败。
- **本仓计数**：5（截至 2026-11-24），其中 01-5 发生在本模式点名之后，触发完整复盘（见 docs/dev/reviews/2026-11-24-d6-d7-display.md）
- **为什么在这个仓库反复发生**：采集链路长（本机或 ssh → agent → 缓存 → 看板、终端、状态栏），每一层都有现成的默认值可退：缓存里有上一次的结果，`except` 后 `return cwd` 或 `return None` 也都能让界面继续画下去。界面能画出来，就没人发现。
- **写代码时如何预防**：
  - 失败要变成数据里的一个字段（如 `git_failed`、`collect_error`），一路带到输出端，由输出端如实显示；
  - 新鲜度一律问 `board.host_freshness()`，不在各处自己比较时间戳（R-002）；
  - `except` 分支里不准只 `pass` 或退回默认值，要么记下失败，要么让调用方知道。
- **评审时怎么查**：对 diff 里每个 `except`、`or <默认值>`、提前 `return`，问「失败时用户在终端、网页、`proj report` 里看到什么」。答案是「和成功时一样」就命中。
- **现有守卫**：guards.md G03（新鲜度单一判定）、G04（git 读取失败标记）。
- **相关铁律**：CLAUDE.md 第 3 条。
- **相邻模式**：07（坏输入直接崩溃，是这个模式的反面：失败太响而且不可诊断）。

## 案例

### 案例 01-1：本机采集失败两小时后，会话仍在「进行中」
- **commit**：`d98c61f`
- **日期**：2026-11-19 发现
- **症状**：本机采集失败两小时后，会话仍然显示在「进行中」，终端页头也不显示原因。远端主机已有过期判断，本机没有。
- **根因**：新鲜度判定只写在远端分支里；本机分支直接用缓存。
- **量化影响**：不可量化：取决于采集失败的时长，最长可达缓存的整个寿命。
- **为什么测试没拦住**：双路径只测一条（只测了远端的过期判断）。
- **钉住它的测试**：`tests/test_host_freshness.py`、`tests/test_freshness_outlets_spec.py`
- **同根因第几次**：第 1 次
- **状态**：已修（R-002）

### 案例 01-2：git 读取失败被当成「不是 git 仓库」
- **commit**：`d98c61f`
- **日期**：2026-11-19 发现
- **症状**：大仓库的 `git status` 超过 5 秒就超时。终端把这个项目标成 `non-git`，`proj report` 里这个项目直接消失。
- **根因**：git 调用的所有失败（超时、权限、损坏）都走「不是仓库」的分支。
- **量化影响**：不可量化：取决于有多少仓库会超时。
- **为什么测试没拦住**：失败静默无信号，夹具里没有会超时的仓库。
- **钉住它的测试**：`tests/test_git_failed_spec.py`
- **同根因第几次**：第 2 次（与 01-1 同根：失败退回成正常值）
- **状态**：已修。GIT_TIMEOUT 没有加长，原因写在设计里：collect 对项目顺序执行，加长会拖垮整台主机的采集。

### 案例 01-3：ssh 连不上时，restore 报「trash is empty」
- **commit**：`d98c61f`
- **日期**：2026-11-19 发现
- **症状**：
  - ssh 连不上时，`restore` 报「trash is empty」；
  - 在 zellij 里新开标签页失败时，带着 traceback 退出；
  - 对非 git 目录按 `^X`，`proj` 直接退出。
- **根因**：失败路径复用了「正常但为空」的输出分支，或者根本没有失败分支。
- **量化影响**：不可量化。
- **为什么测试没拦住**：这些失败路径零测试（评审把实现改错，测试照样全过）。
- **钉住它的测试**：`tests/test_failure_paths.py`、`tests/test_failure_paths_spec.py`、`tests/test_failure_coverage_spec.py`
- **同根因第几次**：第 3 次
- **状态**：已修

### 案例 01-4：`agent.project_root_for` 在 git 失败时静默退回 cwd
- **commit**：无，2026-11-21 /retro 同族横扫时发现；966fdab 之前就存在
- **日期**：2026-11-21
- **症状**（推断，未复现）：`git rev-parse --show-toplevel` 超时或失败时，会话被归到它的 cwd，而不是仓库根目录。如果 cwd 是子目录，看板上会冒出一个不存在的「项目」。
- **根因**：`except Exception: pass`，然后 `return cwd`。
- **量化影响**：不可量化：需要 git 失败，并且会话的 cwd 是子目录。
- **为什么测试没拦住**：01-2 修复时没有对 agent 里其余的 git 调用做同族横扫。
- **钉住它的测试**：无，属于欠账，见 docs/backlog.md「同族横扫：project_root_for」。
- **同根因第几次**：第 4 次
- **状态**：待修

### 案例 01-5：终端里「等你」行盖住了同项目里状态读不准的会话
- **commit**：`4f1c0e4`（run 2026-11-23-d6-d7-display 压缩提交；问题由终审 I-3 发现，F-3 修复）
- **日期**：2026-11-23
- **症状**：
  - 条件：brief 主机上，同一项目里同时有一个 waiting 会话和一个 `state_error` 的 idle 会话。
  - 终端：由 waiting 会话代表这个项目，行尾没有 `⚠ 状态读取失败`。出错的会话在列表和预览里都看不到。
  - 摘要行：却写着「另有单独列出的 空闲 1：出错 1」。
  - 网页：把出错的卡片单列出来，与终端不一致。
- **根因**：终端一个项目只画一行，由「代表会话」决定行的内容。出错标记只看代表会话本身，没看同项目里其他没折叠的会话。
- **量化影响**：只在实现主机上出现，而且要求同一项目同时有 waiting 和出错会话。合并前就修掉了，没有进入交付。
- **为什么测试没拦住**：只测了「折叠的 busy 加出错的 idle」，没测「waiting 加出错的 idle」。两个出口（网页按会话、终端按项目）的粒度不同，各自的测试都只喂了自己那一种形态。
- **钉住它的测试**：`tests/test_ui_brief.py::test_waiting_row_carries_the_mark_when_its_project_has_an_errored_idle`，以及它的两条反面用例（没有出错邻居、非 brief 主机时不加标记）。
- **同根因第几次**：第 5 次（本模式点名之后复发）。
- **状态**：已修。相邻模式：08（摘要文字与终端显示两份口径）。
